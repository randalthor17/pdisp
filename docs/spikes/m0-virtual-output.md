# M0 spike: virtual output (vkms vs evdi)

Date: 2026-11-21. Host: NixOS 26.11, kernel 6.18.63 (nixpkgs), niri 26.04, GPU Navi 44 (RX 9060 XT, card1)
plus Raphael iGPU (card0). Throwaway code: `tools/spikes/evdi_spike.c`.

## Verdict

| Question | Answer |
|---|---|
| vkms configfs with per-connector EDID | **No.** See below. Plan item 1 must change. |
| evdi gives EDID identity, hotplug, frames | **Yes** (all verified below). |
| niri accepts the output as a normal monitor | **Yes**, for both vkms and evdi. |
| VAAPI HEVC low-latency encode on the 9060 XT | **Yes**: ~2 ms/frame, no B-frames, 60 fps live from evdi frames. |

## vkms

- Kernel 6.18.63: `CONFIG_DRM_VKMS=m`, but no configfs support at all. Loading it gives
  `/sys/kernel/config` with no `vkms` directory, one fixed `Virtual-1` connector, `edid` file 0 bytes,
  physical size unknown, always `connected`. niri shows it as "Unknown Unknown Unknown".
- Upstream source (kernel.org): configfs arrives in v6.19 (`select CONFIGFS_FS`). Connector attributes there
  and in v7.0 are only `status` (connected/disconnected/unknown). **No EDID attribute**, and none on master
  (0 mentions of "edid" in `vkms_configfs.c`). The vkms docs list EDID control as future work.
- So even on a newer kernel vkms gives hotplug but no EDID: no stable identity, no physical size.

## evdi 1.15.1 (nixpkgs `linuxPackages.evdi`, out-of-tree)

Commands:

    nix build nixpkgs#linuxPackages.evdi                      # module built for 6.18.63, vermagic matches
    pkexec insmod <store>/lib/modules/6.18.63/.../evdi.ko.xz initial_device_count=0
    pkexec sh -c 'echo 1 > /sys/devices/evdi/add'             # creates /dev/dri/card3
    ./evdi_spike 3 25 out.ppm                                 # lib API: evdi_open/evdi_connect2/...

Verified:

- Module loads on 6.18.63 (README says DisplayLink verified only to 6.15; no issue seen here).
- EDID generated by us (128-byte base block, passes `edid-decode` clean): 2400x1080@60 RB, 148x66 mm, name
  `pdisp-phone`, serial `PDISP0001`.
- niri shows `Output "PNP(PDI) pdisp-phone PDISP0001" (DVI-I-1)`, mode 2400x1080@59.997 (preferred), auto scale 2.5.
  Physical size shows 150x70 mm: niri uses the base-block cm fields, not the DTD mm fields.
- Hotplug: `evdi_disconnect` removes the output from niri; `evdi_connect2` with the same EDID brings it back
  with the identical output name. 3 s gap in the test.
- Frames: `evdi_request_update`/`evdi_grab_pixels` return real desktop content (wallpaper, bar; checked as PNG).
  BGRA, stride = width*4. Grab cost 1.0 to 1.5 ms per 2400x1080 frame (a memcpy of ~10 MB, user to kernel buffer).
  Updates only arrive when something changes (static desktop = no frames); ~16.7 ms cadence during animation.
- Cursor events are available (`evdi_enable_cursor_events`).

Findings that change the design:

- **Dirty rects exist but are one bounding box per update.** An idle desktop (shell animation only) reported
  full-screen rects (0 of ~67 partial). With a window moving (see encode spike below), 533 of 565 updates were
  partial (average 44% of the screen) and never more than one rect per update. So damage is usable as a hint
  (for example skip static refinement, or limit work), but not as a precise region list.
- Connector name is `DVI-I-n` and depends on device index. Stable identity comes from the EDID (make/model/serial),
  so the output config in niri should key on that, not the connector name.
- evdi has no GPU: niri renders on the dGPU and copies into evdi's buffer. The cost of that copy under load is
  **unverified** (the idle test above shows nothing).
- Capture does not need `CAP_SYS_ADMIN` or `drmModeGetFB2`: libevdi hands the frame to the app directly.
  The only privileged step in the test was `insmod` and the sysfs `add`. `/dev/dri/cardN` was usable by the
  seat user via ACL.

## VAAPI HEVC encode spike (RX 9060 XT, ffmpeg-full 9.0.2, Mesa 26.3.0 radeonsi, `/dev/dri/renderD128`)

Synthetic source (`testsrc2` 2400x1080@60, NV12 upload):

    ffmpeg -vaapi_device /dev/dri/renderD128 -f lavfi -i testsrc2=size=2400x1080:rate=60 -frames:v 600 \
      -vf format=nv12,hwupload -c:v hevc_vaapi -b:v 30M -maxrate 30M -bf 0 -g 120 -async_depth 1 -f hevc enc.hevc

- 535 fps (8.9x realtime). Encoder packet latency ~1.8 to 3.0 ms per frame (`-benchmark_all`, receive-packet stage;
  submit stage is a few microseconds).
- `ffprobe`: HEVC Main, yuv420p, 2400x1080, `has_b_frames=0`, frames only I/P (IDR every 120). `mpv` decodes it.

Live chain, real captured frames (evdi -> raw BGRA fifo -> `hwupload,scale_vaapi=format=nv12` -> `hevc_vaapi`),
with an mpv `testsrc2` window moved onto the virtual output with `niri msg action move-window-to-monitor`:

- 565 frames in 14 s; after the first 6 s (motion) 59.9 fps with a max inter-frame gap of 19 ms,
  so niri kept up at 2400x1080@60 and evdi grab stayed at 1.0 to 1.6 ms.
- ffmpeg consumed it in real time (`speed=1x`, 0.6 s user + 0.9 s sys CPU for 14 s). Output ~18.8 Mbit/s average
  (VBR under a 30M cap), decodes to the right picture (checked as PNG).
- Caveat: BGRA->NV12 via `scale_vaapi` tags the stream `yuvj420p` (full range). Color range/matrix tagging must be
  set deliberately in M10 so the phone decoder matches.
- Not isolated: the compositor-side copy cost (niri render + copy into evdi). Only the end result (60 fps held,
  no stalls) is known. A heavier test (full-screen video, 4K scale) is still open.

Intra refresh and "no keyframe spikes" were not tested; `-g 120` IDR intervals are the only structure so far.

## Load check: 2304x1440@90 fullscreen video (tablet-class mode)

EDID mode set with `MODE=2304x1440@90` (edid-decode: 332.64 MHz, 234x150 mm, 135 kHz). Source: a pre-rendered noisy
90 fps clip (`testsrc2` + `noise`, 150 Mbit/s HEVC) played by `mpv --hwdec=vaapi --vo=gpu`, moved to the virtual
output and fullscreened with `niri msg action move-window-to-monitor/fullscreen-window`. Encode: `hevc_vaapi`,
CBR 40M, bufsize 1500k, `-bf 0`, one IDR only (`-g 100000`).

- 888 frames in 10 s (88.8 fps, target 90), mean gap 11.3 ms. 861 of 888 updates were full-frame rects. Max gap 113 ms,
  6 gaps over 20 ms (likely the clip looping every 3 s; not confirmed). evdi grab avg 1.96 ms, max 3.36 ms for a 13 MB frame.
- Encoder kept pace (`speed=0.99x` on the live fifo input); P-frames avg 54 KB (~39 Mbit/s at 90 fps), max 155 KB.
- So niri + evdi + VAAPI sustain 2304x1440@90 on this machine with a full-screen high-motion source.
  The copy into evdi's buffer is not separately measurable, but it is not the limit here.
- Pitfall found in the spike itself: after a synchronous `evdi_request_update` success, waiting in `poll` for an
  event caps delivery at the poll timeout (10 fps at 100 ms) and back-pressures the compositor (mpv then dropped
  frames). The real daemon must loop on `request_update` while it returns true and only block when it returns false.

## Keyframes, intra refresh and rate control

- libva reports `VAConfigAttribEncIntraRefresh` = rolling column, rolling row and P-frame for HEVC on this GPU
  (also `EncROI` with 32 regions, `EncMaxRefFrames` l0=2, max width 4096). `ffmpeg`'s `hevc_vaapi` has no option for it,
  so intra refresh can only be used from direct libva code. **Advertised, not tested in practice.**
- Keyframe spike is real on desktop content. Capture of a moving window at VBR 30M, `-g 120`: I-frames avg 393 KB
  (max 728 KB) vs P-frames avg 53 KB (max 169 KB).
- Re-encoding that capture with a tight CBR buffer fixes most of it without intra refresh
  (all with `-bf 0`, hardware encode, PSNR against the decoded source):

  | Setting | I avg / max | P avg / max | rate | PSNR avg / min |
  |---|---|---|---|---|
  | VBR 30M `-g 120` | 206 / 342 KB | 58 / 90 KB | 29.2 Mbit/s | 55.7 / 52.9 dB |
  | CBR 20M buf 2 Mbit `-g 120` | 134 / 209 KB | 42 / 79 KB | 21.1 Mbit/s | 54.4 / 49.0 dB |
  | CBR 20M buf 700 kbit `-g 120` | 73 / 92 KB | 42 / 76 KB | 20.7 Mbit/s | 53.3 / 49.0 dB |
  | CBR 20M buf 700 kbit, no periodic IDR | one IDR only | 43 / 76 KB | 21.0 Mbit/s | 53.7 / 52.5 dB |

  A 700 kbit buffer holds the I-frame to about the largest P-frame at a ~2 dB PSNR cost on this content. The source was
  already compressed, so these PSNR numbers are optimistic for text and need re-checking on raw capture in M10.
- Design implication: no periodic IDR. Send an IDR on connect and on request (loss, decoder reset), use CBR with a
  small VBV buffer, and add intra refresh through libva only if keyframe-on-demand proves too bursty over Wi-Fi.

## Not yet verified

- Raw-capture quality on text (the PSNR table uses an already-compressed source).
